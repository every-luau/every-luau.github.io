## One problem per library

each library solves one problem: `Thread` recycles threads, `Signal` fires handlers, `Void` cleans
up. if a feature is a different problem, it goes in a new library that can depend on the old one,
so a project only installs what it uses

using another library to build yours is a dependency, not a new problem. `Observe` has
`Observe.players`, `Observe.character`, `Observe.tools` and the rest, and they all use `Observable`,
so they stay in one library

## Dependencies

libraries build on each other to get the best API possible: `Observable` uses `Stream`, `Brio` and
`Void`, etc. a library can also depend on a package from outside every, the way `Weight` uses [`rbx-cryptography`](https://github.com/daily3014/rbx-cryptography)

## Simplest API 

a library gives its users the functions they need, so they do not have to require another package
just to use it. `Signal:connect` hands back a `Connection`, for example, but you never require
`Connection` yourself

## Clean up after yourself

anything that creates connections, threads or instances can be cleaned up. `Connection` has
`disconnect`, `Signal` and `Observable` have `destroy`, and each of them can be added to a `Void`
so a single `clean` call removes everything

## Naming

- modules and their folders are PascalCase: `Signal`, `BetterScale`
- packages on ember are kebab-case: `every/signal`, `every/better-scale`
- classes and types are PascalCase: `Connection`, `SignalLike`
- functions, methods and variables are snake_case: `from_signal`, `attach_to_instance`
- constants are SCREAMING_SNAKE_CASE: `MAX_IDLE`

## Structure over speed

every cares more about structure than raw speed, because readable code is easier to review, fix and
extend. a library still has to be fast. optimize where it helps, but keep the code readable for the
next person

## Comments

comments are meant to stay. do not strip them when you refactor or optimize: they are how other
developers understand what you did and why.

## Tested before release

every public function has a test in the library's `tests` folder. a release only goes out once
they all pass, and CI runs them again on every push and pull request

## Docs ship with the code

when a change affects how a library is used, update its doc comments, examples and README in the
same pull request. a release should never document an older version of the library

## AI usage

write library code yourself and keep AI out of it as much as you can. if you want a library you
cannot write, open an issue that describes it. someone may build it if it is useful and fits this
page

AI is fine for documentation, as long as the result is easy to read. remove `--` and other dashes
used to join sentences, and reword anything that sounds generated
